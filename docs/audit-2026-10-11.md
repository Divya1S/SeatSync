# SeatSync codebase audit

Audit date: 2026-10-11. Scope: the whole repository (six Spring Boot services,
the Angular frontend, contracts, infrastructure, CI, documentation). Every
finding below was verified against the code, not inferred from the README, and
every fix has a test. Section 7 records what was run and what the results were.

## 1. What the system is

A reserved-seat booking platform whose single load-bearing invariant is that a
seat is never sold twice and sales never exceed capacity, including under
concurrent load and partial infrastructure failure. Architecture, flows and
trade-offs are described in `README.md` and `docs/architecture.md`; the
cross-service contract is `docs/CONVENTIONS.md`. In one line per component:

| Component | Role | Data |
|---|---|---|
| `api-gateway` (Spring Cloud Gateway, WebFlux) | routing, edge JWT validation, per-IP rate limiting, CORS | Redis (limiter buckets) |
| `auth-service` | register/login, HS256 access tokens (15 min), rotating refresh tokens (7 d), logout | Postgres `seatsync_auth` |
| `catalog-service` | venues, events, derived seat maps, public search, Redis cache-aside | Postgres `seatsync_catalog`, Redis |
| `booking-service` | holds (Redis `SET NX` + DB row), version-guarded confirm, cancel, waitlist, expiry sweeper, transactional outbox, idempotency, STOMP live seat state | Postgres `seatsync_booking`, Redis, Kafka (producer) |
| `notification-service` | consumes the three Kafka topics with claim-before-send dedupe, retry topics and a DLT, sends email | Postgres `seatsync_notification`, Kafka (consumer), SMTP |
| `ai-concierge-service` | Spring AI RAG over five policy documents (pgvector) plus three read-only tools against catalog and booking | Postgres `seatsync_ai` (pgvector), OpenAI (optional) |
| `frontend` (Angular 21, nginx) | SPA: catalog, live seat map, bookings, organizer dashboard, chat widget | localStorage (tokens) |

Critical workflows: hold → confirm (`HoldService.createHold`,
`BookingService.confirm`), hold expiry and waitlist cascade
(`HoldExpiryService`, `WaitlistService.offerSeat`), event delivery
(`BookingEventPublisher` → `OutboxRelay` → Kafka → `NotificationService`),
and the concierge turn (`ConciergeService.chat`).

## 2. Highest-risk areas (before this audit)

1. **Hold expiry sweep.** One transaction per sweep, side effects emitted
   before commit, and any exception crossing a transactional proxy marked the
   whole batch rollback-only. One bad hold could stall expiry for every hold.
2. **Outbox relay under a broker outage.** Sequential sends inside the claim
   transaction: up to 100 × `max.block.ms` with row locks and a pool
   connection held.
3. **Session security.** No logout or refresh-token revocation; no reuse
   detection; shared HS256 secret with a committed default; issuer not checked
   at the gateway or in three services.
4. **Concierge input boundary.** Organizer-written text relayed verbatim into
   the model context; no per-turn tool budget; unbounded in-memory
   conversation store keyed by client-chosen ids on a public endpoint.
5. **Data quality of outbound events.** An empty `eventName` could be emitted
   when catalog was unreachable, violating the project's own JSON Schema.

## 4. Security review

Checked: authentication and authorization (path rules plus owner checks in
services), IDOR (holds, bookings and events are owner-checked; non-owners get
404 for drafts), injection (JPA parameters throughout; native queries use
named parameters; LIKE now escaped; Angular escapes interpolation and
`innerHTML` is not used), secrets (no real secrets committed; the development
JWT secret and demo passwords are documented defaults and now logged as a
warning at startup), CORS (gateway only, credentials to one origin), JWT
validation (signature, expiry, type and now issuer at every hop), rate
limiting and abuse (per-IP, remote address by default, per-user hold cap,
separate chat budget), PII in logs (masked), container privileges (non-root),
prompt injection (tool output compacted and declared as data; tools remain
read-only and carry no credentials).

Not performed: a Maven dependency vulnerability scan (no OWASP
dependency-check or similar is configured; it needs an NVD feed download and
an API key to be useful in CI). The frontend `npm audit` result is recorded in
section 7.

Remaining risks are listed in section 6.

## 5. Code quality and architecture

Kept as they are, because they are reasonable: service boundaries, the
three-layer hold design, the outbox, the conventions document, ArchUnit rules,
RFC 7807 everywhere. No framework or dependency was added or upgraded.

Improved: failure isolation in the sweeper; explicit compensation in the hold
path; a durable tier for event names instead of a process-local cache;
classified failure handling in the relay; bounded buffers and stores
(request bodies, chat memory, name cache); validation on query parameters.

Remaining debt: the public path list is duplicated between the gateway and
each service's security configuration; `SeatQueryService.liveSeats` reads
every seat row per request; the relay still sends inside its claim
transaction (bounded now, structurally a two-phase claim/mark would be
better); the concierge embeds each question twice (its own search for
provenance plus the advisor's).

## 6. Remaining issues, in priority order

1. **Shared HS256 secret with a committed default.** Any service holding the
   secret can mint tokens. Move to RS256 with a JWKS endpoint so only
   auth-service signs; inject the key from a secrets manager; fail startup
   without it in non-local profiles.
2. **Tokens in `localStorage`.** XSS-exposed. Use an httpOnly, SameSite
   refresh cookie and keep the access token in memory.
3. **Rate limiter fails open when Redis is down** (Spring default). Fail
   closed on write routes or add a local in-memory fallback bucket.
4. **No database-level uniqueness for active holds.** One active hold per
   seat is enforced by Redis plus a check-then-act read. A partial unique
   index on `holds(event_id, seat_id) WHERE status='HELD'` would make it a
   constraint, but today it would also reject a new hold while an expired
   one is waiting for the sweep (up to 10 s); `createHold` must expire a
   stale row first. Correctness is unaffected either way: confirm's version
   check is the guard.
5. **Live seat view and seat-map rendering do not scale** past a few thousand
   seats (full read per request; one button per seat). Needs a per-event
   projection and section-level loading.
6. **Concierge quality is unmeasured.** No golden question set, no
   faithfulness check; confidence is a retrieval-score heuristic plus a
   phrase match; memory is per instance. Build an evaluation harness before
   any production claim; move memory to Redis or JDBC.
7. **Kafka replication factor 1, single Postgres, single Redis, Compose-only
   deployment, plaintext transport, no dashboards or alerts.** The runbook
   names the signals (outbox age, DLT depth, consumer lag); nothing emits
   alerts.
8. **No end-to-end or component tests for the frontend** (pure functions and
   services are unit-tested).
9. **Admin cannot cancel another user's booking or release their hold**; a
   support workflow will need it.
10. **Gateway keeps routing to a dead replica for 1–2 minutes** (measured in
    the kill-node test): add retry-on-connect-failure and outlier ejection.
11. **The nginx frontend image still runs as root** (`nginx:1.27-alpine` default);
    switch to `nginxinc/nginx-unprivileged` or add a `USER` with a writable cache dir.
12. **Application rollback across a Flyway migration.** All migrations are
    additive, so an older build runs fine against a newer schema, except that
    Flyway's `validateOnMigrate` rejects an applied migration it cannot resolve
    locally. Set `spring.flyway.ignore-migration-patterns=*:future` (or pin
    `target`) before relying on application rollback.
13. **Sweeper throughput is now bounded** at 2,000 holds per 10 s run per
    replica (~200/s). Earlier batches were unbounded in one transaction; large
    expiry storms now drain over several runs. Add replicas or shorten the
    delay if an on-sale regularly expires more than that.

Adversarial self-review (same day) re-read the full diff and traced the changed
code through its callers. It found and fixed: the expiry sweep's new 500-per-run
cap, which would have drained large expiry storms slower than the original
unbounded batch (raised to 2,000 and documented); the email composer treating
a blank `eventName` as a real name; the frontend logout ignoring a refresh token
rotated by another tab; and three places where the new configuration was not
proven to bind (now covered by `BookingPropertiesTest` and
`CorsOriginsConfigTest`, which also proves an unlisted origin is refused). It
also hardened the chat-memory store to hand out mutable copies, as the Spring
AI reference implementation does. Re-runs after those changes: notification 28,
concierge 41 and gateway 29 unit tests green; frontend 24 specs and build green;
booking `verify` green (82 unit + 29 integration, coverage gate met), booking
unit suite green after the extended relay assertion, PIT 192 mutants / 139 killed
(72%, gate 70) green.

Not performed: browser-driven UX verification (no browser automation was
available in this session; the UX changes are limited to labels, a
confirmation dialog and the logout call, all covered by unit tests or
inspection), and a Maven dependency vulnerability scan (not configured).
